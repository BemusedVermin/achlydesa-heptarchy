# M2-02.F1 · Despawning a body must remove its parts

## Goal

When a body is despawned, the parts attached to it go too. Today `sim.World.Despawn` removes only the body, so Ark resets each part's `PartOf` target to the zero entity and the parts stay in the world as orphans with UIDs in the index. A failed spawn (a spawner after `body` errors) leaks parts the same way.

## Context

- M2-02 spawns one part entity per body plan entry, related to the body by `comp.PartOf`.
- Severed parts are meant to outlive their body (grafting, crawling parts), so the fix must remove only parts still attached at despawn, not parts that were cut off earlier.

## Deliverables

- `sim.World.Despawn` (or a hook it calls) removes the parts attached to the entity, children first, and their UID index entries.
- A test: spawn a party, despawn a member, and no `comp.Part` with a zero `PartOf` target remains.

## Spec

`sim` is below `anatomy`, so Despawn cannot import it. Either query `comp.PartOf` directly in `sim` (it already knows `comp`), or add a despawn hook registry like the spawners.

## Acceptance criteria

- [x] Despawning a body leaves none of its attached parts alive; severed parts elsewhere are untouched.
- [x] A spawn that fails after the body spawner leaves no part entities behind.
- [ ] `go tool task check` passes.

## Out of scope

- Death and corpses: M2-07.

## Notes

Done by M2-02.F1: `sim.World.Despawn` collects the entities whose `comp.PartOf` targets the body (before removing the body, since Ark zeroes targets on removal) and despawns them first, recursively. Severed parts have no `PartOf` and are untouched. A failed `Spawn` already calls `Despawn`, so the leaked-parts case is covered by the same change. The test (`TestDespawnRemovesAttachedParts` in `sim`) builds parts by hand because `sim` cannot import `anatomy`. No follow-ups filed.

Triaged by M2-15: todo in M2, because it is a bug in code M2 builds on: M2-08's creatures spawn and die as bodies with parts, and an orphaned part keeps its UID in the index.
