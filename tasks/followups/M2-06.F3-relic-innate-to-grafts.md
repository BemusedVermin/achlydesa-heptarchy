# M2-06.F3 · Relic as innate to grafts

## Goal

A body is offered Relic when it has a graft, and not otherwise, as the game design says Relic is "innate to grafts".

## Context

- Game design, "Combat → Types".
- M2-06 leaves `type.relic` out of every template's `lists.types`, because a choice's offer formula (`OfferEnv`) sees only the actor's template and pack, not what is attached to its body.

## Deliverables

- The actor's parts (at least whether any is a graft) in `content.OfferEnv.Source`, so `choices.cue`'s `type` offer can say `record.id == "type.relic" && source.grafted`, or similar.
- `choices.cue` offers Relic that way. A test: a body with a graft is offered Relic and one without isn't.

## Spec

Suggestion: add `Grafts int` or a `Parts []Record` to `Side` for offers. The shape is open.

## Acceptance criteria

- [x] Relic is offered to a body with a graft and not to one without.
- [x] `go tool task check` passes.

## Out of scope

- Any other type's availability.

## Notes

Until this is done, nobody in the sample content can use Relic.

Done: added `Grafts int` (`source.grafts`) to `content.Side`, filled by `effects.SideOf` from the body's attached parts (it counts every body it is asked about, so `target.grafts` works too). The `type` offer in `choices.cue` now also offers `type.relic` when `source.grafts > 0`. It is an addition to the existing offer, so a template that lists Relic innately (as the test fixtures do) still gets it. Test: `TestRelicIsOfferedOnlyToABodyWithAGraft`. Regenerated `env_go_gen.cue`. No follow-ups filed.
