# M3-04.F2.F1 · Give bodies a content-named set of state flags instead of one component per marker

## Goal

A yes/no fact about a body (dead, downed, protected, a corpse a consumer may eat) is a flag whose name is content. Adding one needs no new Go component, and formulas can read any flag by name.

## Context

- Each such fact is its own empty or near-empty component today in `internal/core/comp/comp.go`: `Controlled`, `Protected`, `Downed`, `Reattached`, and `Dead` (with a tick). Every new one costs a Go type, a registration, a save bump and, for formulas, a hand-written field on `BodyEnv`.
- M3-04.F2 added `ActionDef.Corpse`, a fixed Go field, so one action could say it may target a dead body. The next such fact needs another field or component by the same route.
- AGENTS.md rule 4 (content is data) and `docs/go-technical-design.md`, "Designing for pivots", prefer tags and named formulas over code that names a rule. Content records already carry generic tags (`Vocabulary.Tags`); bodies have no equivalent.
- The cost to weigh: a flag set is one component holding a sorted list of IDs. A marker component lets the ECS query by archetype, so a per-tick scan for "all dead bodies" is cheaper as a component than as a flag test. The save format and hash must stay deterministic: sort the flags by ID.

## Deliverables

- `internal/core/comp/comp.go`: a `Flags` component holding flag IDs (`flag.dead` and the like), with add, remove and has helpers, registered and saved.
- `internal/content/types.go` and `content/data/flags.cue` (new): flag records, so a flag has a name and a content-owned meaning, and an unknown flag in content fails at load.
- `internal/content/env.go`: `BodyEnv` exposes the set to formulas, for example `source.has("flag.corpse")`; schemas regenerated.
- A migration of one existing marker as the proof, suggested `Protected`; the others follow in their own tasks.
- Tests, and `internal/core/save/save.go`: bump `CurrentVersion`.

## Spec

Suggestion, not firm: keep the marker components that the engine queries every tick (`Dead`, `Downed`) as components, and move the facts that content reads but the engine rarely scans (`Protected`, `Reattached`, a corpse's edibility) to flags. A flag is added and removed by effects (`set_flag`, `clear_flag`) so that content can create state too.

Design questions for the owner to settle first, because this is more than a refactor:

1. Flags only for facts content may read, or also for facts only code reads?
2. Do flags carry a value (a tick, a counter) or only exist? `Dead` carries a tick today.
3. May content define a new flag freely, or only code-registered ones?

## Acceptance criteria

- [ ] The migrated marker behaves as before: `go tool task same-behavior` shows no change.
- [ ] A test adds a flag from content only, with no Go change, and a formula reads it.
- [ ] `go tool task check` passes.

## Out of scope

- Moving `Dead` and `Downed`, until the scan-cost question is measured.
- Replacing `ActionDef.Corpse`: a follow-up once flags exist.
