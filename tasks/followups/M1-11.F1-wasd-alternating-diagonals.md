# M1-11.F1 · WASD: up and down zigzag diagonally

## Goal

`w` and `s` move the party straight up and down the screen on the hex grid by alternating diagonal steps, so the six hex keys are no longer the only way to move vertically. The owner's one complaint with the M1-11 controls.

## Context

- M1-11 binds `q e a d z c` to the six steps (`step/nw`, `step/ne`, `step/w`, `step/e`, `step/sw`, `step/se`). A pointy-top hex grid has no straight up or down, so going vertically means alternating NW and NE (or SW and SE) by hand.
- In the double-width layout hex (q, r) is at column `2q + r`, row `r`. NW moves one column left, NE one column right, so alternating them holds the screen column steady.
- Rule 7 (`AGENTS.md`): keys bind to option IDs and choices come from the view. The alternation is a frontend choice among offered options; it must not send a command the view doesn't offer.

## Deliverables

- `internal/frontend/tui/keys.go`: `w` and `s` bindings, resolved to a step option ID.
- `internal/frontend/tui/keys_test.go`: tests for the resolution.
- `internal/frontend/tui/render.go` or `app.go`: only if the alternation needs state.

## Spec

Suggestion: `w` picks `step/nw` or `step/ne`, `s` picks `step/sw` or `step/se`, so the leader stays on one screen column.

- Stateless option: pick by the leader's column parity relative to the column where the vertical run began. This needs the run's anchor column, so keep it in `App` and reset it on any non-vertical key.
- Simpler option: remember the last vertical option and flip it. Reset when another movement key is pressed.
- If the preferred diagonal is absent or disabled, fall back to the other one (and show the reason only if both are blocked), so a wall doesn't stop the zigzag.
- `q e z c` keep their meaning, and `a d` stay west and east. The help line lists `w s` when a vertical step is offered.

Open question for the owner: should the first `w` after another move go NW or NE? Recommendation: whichever is offered, preferring NE.

## Acceptance criteria

- [x] Pressing `w` repeatedly on open ground moves the leader straight up the screen, with the column unchanged every second step; `s` does the same downward.
- [x] When the preferred diagonal is blocked, the other is used; when both are, the status line shows the reason and nothing is sent.
- [x] Pressing any other movement key resets the alternation.
- [x] `go tool task check` passes.

## Out of scope

- Remapping or removing `q e z c` (the keymap may change in a later task).
- The action menu and look mode (M2-10).

## Notes

Triaged by the owner: first `w` after another move goes NE, as recommended.

Implemented: `w` tries NE then NW, `s` tries SE then SW. State is `lastVertical` on `mapScreen`: the option the last `w`/`s` sent; the other diagonal is tried first next time. It resets on any key other than `w`/`s` (not only movement keys), and a blocked step does not record. Resolution is the pure `VerticalOption` in `keys.go`, tested in `keys_test.go`. If both diagonals are disabled, `App.Choose` shows the first one's reason and sends nothing; if neither is offered nothing happens. The help line lists `w s` when any diagonal step is offered. `a d q e z c` unchanged. Acceptance criteria 1 and 3 are covered by the unit test of the resolution, not an end-to-end key test. Files touched outside the list: `mapscreen.go` (holds the state). No follow-ups filed.
