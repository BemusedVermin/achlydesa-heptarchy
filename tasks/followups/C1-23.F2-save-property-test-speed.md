# C1-23.F2 · Bring the save property test under 2 seconds

## Goal

`TestLoadingAfterRandomPlayContinuesIdentically` (`internal/core/save/save_test.go`) runs in under 2 seconds, the target C1-23 set.

## Context

- C1-23 built the registry once, cut the slices to `before` 0..20 and `after` 0..10, and compares hashes after the load and at the end instead of after every command. The test went from 24s to about 9-12s on a machine shared with other test runs.
- A CPU profile of what is left: about half is play itself (`Game.Apply` and `Game.View`: `timeline.decisionTick`, `actions.usableChannels`, `hexmap.computeVisible`), and about a third is `Game.Hash`, where `canonical` and `normalize` in `internal/core/game/save.go` decode and re-encode the whole world JSON twice.
- rapid runs 100 cases by default and offers no per-test count; only the global `-rapid.checks` flag changes it.

## Deliverables

One or more of:

- A cheaper `canonical`: sort keys in a single pass instead of the marshal, decode, marshal round trip in `normalize`.
- Cheaper view building on a step that does not need the whole view (the harness `Step` builds one per choice).
- Fewer rapid cases for this test, if the owner accepts the weaker search (for example by drawing fewer, longer games).

## Spec

Any speed-up must keep `Game.Hash` byte-identical for equal games: `go tool task same-behavior` must show no hash change.

## Acceptance criteria

- [x] `go test ./internal/core/save -run TestLoadingAfterRandomPlayContinuesIdentically` takes under 2s on an idle machine.
- [x] `go tool task same-behavior` passes.
- [x] `go tool task check` passes.

## Out of scope

- Changing what the property checks.
