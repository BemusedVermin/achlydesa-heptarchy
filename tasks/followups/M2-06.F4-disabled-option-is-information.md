# M2-06.F4 · A disabled option is information: Name and Keepsake on the wrong body

## Goal

The owner decides whether Name and Keepsake are refused on a body they don't belong to.

## Context

- M2-06 refuses Name and Keepsake (a `requires` over the pack, with a refusal text) when the pack holds no such item bound to the target. The menu then tells the player whose name or keepsake they hold, which could undercut telling holders from false positives.
- Immunity doesn't refuse: the swing lands and does nothing, so a part's material isn't told before it is learned.

## Deliverables

- A decision recorded in `docs/game-design.md`, and a content change in `content/data/types.cue` if the answer is not "keep the refusal".

## Spec

**Decided by the owner:** Name and Keepsake are not refused, since refusing leaks too much information. Drop `requires` from both and let the swing land and do nothing (a `damage` amount formula that checks the pack), as immunity does.

- [ ] The question is answered in the design doc.

## Out of scope

- The investigation system's use of names (post-MVP).

## Notes

- Content: `type.name` and `type.keepsake` lost `requires`, `refusal` and their two refusal texts. A new rule `rule.unheld` (rules.cue) is folded into `rule.immune`, so Strike, Sweep and Sever all land and do nothing when the pack holds no name or keepsake usable on the target. The rule names the two type IDs and items in content, not in Go.
- Code, outside the content-only plan: `checkConsume` (`internal/core/combat/effects.go`) refused Keepsake with "The pack has no keepsake" whenever none was bound to the target, which leaked the same thing. A bound item held for another body now passes the check; `applyConsume` still takes only the stack bound to the target, so a keepsake held for someone else is not used up.
- Keepsake is now used up when the swing lands, after the form's damage, not when it starts (`type.keepsake` no longer uses `#Consumable`). Reason: `rule.unheld` reads the pack at landing, and a start-time consume would empty it first, so a keepsake on its owner would do nothing. A swing interrupted before it lands therefore no longer costs the keepsake. Easy to revert if the owner wants it spent on start.
- Keepsake with no keepsake in the pack at all is still refused ("The pack has no keepsake"), while Name is always offered. This is deliberate: an empty pack says nothing about whose item it is. Name is an innate type, so it is always on the menu.
- Tests updated: the Name refusal tests now expect it offered, landing and doing nothing; added tests for Keepsake on the wrong body and Name on its owner.
- The first acceptance criterion is left unticked: a task branch can't edit `docs/`. Follow-up filed: M2-06.F4.F1 (the wording to add to `docs/game-design.md`).
