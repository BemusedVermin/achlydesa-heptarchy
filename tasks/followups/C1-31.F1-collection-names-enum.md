# C1-31.F1 · Collection names as an enforced set

## Goal

A content field that names a record collection (`"types"`, `"items"`, ...) takes a named Go type whose constants are the collection names, so the schema rejects a typo such as `from: "tyeps"` at `cue vet`.

## Context

- C1-31 made the fixed string sets that had Go constants (`TargetKind`, `TriggerRole`, `ValueKind`) enforced CUE disjunctions, through the cuefix rewrite of `#X: string // #enumX`.
- The collection names are also fixed in Go, but as string literals in the `collections()` table (`internal/content/records.go`), not as constants. So C1-31 left them as plain strings.
- Fields that name a collection:
  - `ChoiceDef.From` (`internal/content/types.go`), checked by `checkChoices` (`choices.go`) through `recordCollection`, which also requires the collection to carry `Data`.
  - The values of `Vocabulary.Lists` (`"materials.<list>": "types"`), and the keys of `Vocabulary.Tags`. Map keys can't take a disjunction directly; they would need a pattern constraint.

## Deliverables

- `internal/content/types.go`: a `Collection` string type with a constant per collection; `ChoiceDef.From` (and `Vocabulary.Lists` values) take it.
- `internal/content/records.go`: `collections()` uses the constants.
- Regenerated schemas (`go tool task schema`).

## Spec

- Keep the Go check in `checkChoices`: it also refuses a collection without `Data`, which the schema can't tell.
- Content files stay unchanged.

## Acceptance criteria

- [x] `go tool task content` rejects `from: "tyeps"` in a scratch file.
- [x] `go tool task same-behavior` shows no change.
- [x] `go tool task check` passes.

## Out of scope

- Content-declared vocabularies (tags, grant kinds).
